### Agentic Design Tenets

Six design tenets govern how agents are built, deployed, and governed within the Kairos architecture. These are architecture-level principles — vendor-agnostic and applicable across front office (voice, chat, email), middle office (quality, compliance, analytics), and back office (document processing, claims, reconciliation) use cases in any industry.

| Tenet | Principle | Kairos Mapping |
|---|---|---|
| **1. Separate Brain, Hands, and Memory** | The reasoning engine (brain), the tools it calls (hands), and the persistent state (memory) are three independent, loosely coupled components. Any can be replaced without rewriting the others. | Brain = Harness governance (playbooks, policies, guardrails). Hands = Skills Library (reusable, model-agnostic tools). Memory = ICF (session context, entity context, decision traces). |
| **2. Stateless Execution, Durable Context** | Every agent invocation is stateless. All state — conversation history, entity context, decision traces — lives in the ICF, not in the agent process. If an agent process fails, another picks up from the last ICF checkpoint with zero state loss. | Enables horizontal scaling and fault tolerance. No sticky sessions. Any compute instance can serve any interaction. |
| **3. Credential Isolation** | Agents never hold credentials directly. All tool access goes through scoped skill proxies with minimum-privilege permissions. Credentials are managed at the platform level, not the agent level. | Skills Library tools are accessed through governed interfaces. PCI, PHI, and PII credentials are never exposed to the reasoning layer. |
| **4. Decision Traceability** | Every agent action — input, reasoning, tool call, output, outcome — is logged durably and immutably. The full causal chain is reconstructable for any decision. | ICF Decision Traces provide explainability for regulators, learning data for the platform, and audit trails for compliance. |
| **5. Disposable Compute** | Agent processes are ephemeral and interchangeable. Treat compute like cattle, not pets. Scale up, scale down, replace failed instances — the Harness and ICF are the durable assets, not the running process. | Harness (rules) + ICF (context) persist. Agent containers are spun up and torn down on demand. |
| **6. Progressive Trust** | Agents earn autonomy incrementally based on accumulated evidence. Start with full human oversight, graduate to exception-only review as confidence builds. | HITL → HOTL → HATL progression. Shadow mode (run alongside humans, compare outcomes) before any cutover. Trust is earned per-skill, per-client, per-domain — not globally. |

These tenets apply identically whether the agent is handling a voice collections call (front office), running auto-QA on processed claims (middle office), or extracting data from mortgage documents (back office). The harness content and skill implementations change per use case; the architectural tenets do not.

## Operations Intelligence (Core — Layer 2)

### Three Modes

Sensors operate in three modes that create enterprise visibility, measure control effectiveness, and enable closed-loop improvement:

| Mode | What It Does |
|---|---|
| **01 Prevention** | Pre-action guidance from plan-aware knowledge, current context, and known risk patterns |
| **02 Detection** | Near-real-time verification — compares calls, documents, and workflow behavior with plan truth and required disclosures |
| **03 Learning** | Misquote patterns, process deviations, and coaching triggers feed closed-loop improvement |

The same data supports upstream prevention, in-flight detection, and downstream learning — turning sensing into sustained operational uplift.

The tagline for Operations Intelligence is "Sensors That See What Humans Miss." When explaining to business audiences, use concrete insight examples to make the three modes tangible:

| Mode | Illustrative Insight | So What |
|---|---|---|
| **Prevention** | "40% of claims flagged as high-risk follow the same three-step pattern." | Agents get pre-loaded with the right context before they start. |
| **Detection** | "12% of interactions are missing a required verification step." | Flagged in-flight, not discovered in a quarterly audit. |
| **Learning** | "Top performers resolve exceptions 3x faster using a workaround." | The pattern is extracted and baked into the standard playbook. |

These examples are illustrative — adapt to the specific vertical and process context. The key message: the same sensor data powers all three modes, turning raw operational signals into sustained improvement.

### Five Sensor Classes

| Sensor | What It Does |
|---|---|
| **Process Mining** | Discovers how processes actually execute from system event logs. Reveals bottlenecks, deviations, and compliance gaps. |
| **Task Mining** | Computer vision-based observation of how users interact with systems. Captures task sequences, workarounds, and undocumented steps. |
| **Conversation Intelligence** | Extracts structured signals from voice and text interactions — intent patterns, sentiment, compliance adherence, quality scores. |
| **Knowledge Mining** | Reverse-engineers operational knowledge from unstructured data (tickets, emails, transcripts). Captures how work actually happens vs. how SOPs say it should. |
| **Doc Intelligence** | Extracts structured data from documents — claims forms, medical records, contracts, correspondence. |

### Should vs. Did
Core intelligence concept. The gap between how processes are documented/expected and how they actually execute. Sensors expose the gap; the harness closes it.

### Guardrail Architecture — Three Tiers

The Guardrails component of the Domain Harness implements a three-tier defense model. Each tier is independently testable and has distinct failure modes. The model is vertical-agnostic and channel-agnostic — it applies to voice (front office), digital (chat, email, SMS), and back-office (document processing, claims) interactions equally.

| Tier | Name | How It Works | Latency |
|---|---|---|---|
| **Tier 1 — Hard** | Deterministic compliance | Rule-based checks (serverless functions, no LLM involved). Binary pass/fail against regulatory requirements. | <5ms |
| **Tier 2 — Soft** | LLM-assessed quality | Quality rubric evaluation running in parallel with output generation to avoid blocking latency. Catches tone, accuracy, and policy violations that rules can't. | Parallel |
| **Tier 3 — Observability** | Batch post-interaction analysis | Drift detection, near-miss analysis, decision authority audits. Runs asynchronously. Findings feed back into tighter Tier 1 and Tier 2 rules. | Async |

**Vertical adaptation:** What changes per vertical is the content of each tier, not the structure. The examples below are illustrative — actual tier content should be designed based on the specific regulatory, compliance, and operational requirements of each engagement:

| Vertical | Tier 1 Hard Rules | Tier 2 Quality Dimensions |
|---|---|---|
| **Collections** | FDCPA/TCPA compliance, PCI redaction, mini-Miranda | Tone, pressure, accuracy, brand voice, playbook adherence |
| **Healthcare** | CMS billing rules, PHI handling, HIPAA disclosure | Clinical accuracy, empathy, plan-specific benefits, coding precision |
| **Mortgage** | RESPA, TILA, fair lending disclosures | Regulatory disclosure completeness, data accuracy, borrower clarity |
| **Banking** | KYC/AML, Reg E/Z, UDAAP | Disclosure timing, product suitability, complaint sensitivity |
| **Insurance** | State-specific claims handling, bad faith prevention | Claim accuracy, policyholder communication clarity, settlement fairness |

### Four-Layer Guardrail Pipeline

Within the three tiers, the runtime pipeline sequences four layers. **This is a reference architecture, not a prescription.** Actual tooling should be designed based on the specific business and technology context of each engagement — the layers define the pattern, not the vendor selection.

| Layer | Function | Example Tools (illustrative) | Latency Target |
|---|---|---|---|
| **Layer 0 — Platform Safety** | First-pass gate. Prompt injection detection, OWASP Top 10 for LLMs, PII/PHI detection, bias detection. | Enkrypt AI, Lakera, Prompt Security, Robust Intelligence. Evaluate for: latency, built-in red teaming, OWASP coverage, multimodal support. | <50ms |
| **Layer 0.5 — Domain Logic** | Custom domain-specific rails. Business and compliance teams author rules in a domain-specific language. Maximum customizability. | NVIDIA NeMo Guardrails (Colang DSL), Guardrails AI, custom policy engines. Evaluate for: DSL expressiveness, business-user authoring, rail library breadth. | 30–100ms |
| **Tier 1 — Deterministic** | Hard compliance rules. No LLM. Binary pass/fail. Blocks prohibited actions. | AWS Lambda, Azure Functions, or any serverless compute. Deterministic, auditable, version-controlled. | <5ms |
| **Tier 2 — Quality Rubric** | Soft quality evaluation. Weighted dimensions. Runs parallel with output generation. | LLM-as-judge pattern (e.g., Claude Haiku, GPT-4o-mini, Gemini Flash). Model choice based on latency/cost/accuracy tradeoff. | Parallel |

> **Note:** The examples above reflect tools evaluated as of April 2026. The ecosystem evolves rapidly — always assess the current landscape when designing a guardrail pipeline for a specific engagement.

### Red Teaming & Continuous Testing

Red teaming in Kairos is continuous, not one-time. Three mechanisms work together:

**Automated adversarial testing (Layer 0):** The platform safety layer should include built-in automated red teaming that adapts and intensifies adversarial prompts based on observed LLM behavior. Examples include Enkrypt AI (29ms prompt injection detection, adaptive attack strategies, OWASP Top 10 mapping) and Lakera (real-time prompt defense). Key capabilities to evaluate: OWASP Top 10 coverage, prompt injection detection latency, bias detection, PII/PHI leakage scanning, and adaptive attack strategies that evolve without manual test design. Actual tool selection should be based on the specific business and technology context.

**Domain-specific rail testing (Layer 0.5 + Authoring & Eval):** Custom domain rails are tested through the Authoring & Eval component of the harness — staging environment, scenario libraries, promote-to-production workflow. For example, NeMo Guardrails uses a Colang DSL that lets compliance teams author and test rails without engineering; Guardrails AI offers a similar capability with a different abstraction. The specific framework should match the team's authoring skills and the engagement's complexity. Business and compliance teams validate rails against known edge cases before promotion to production.

**Observability-driven compounding (Tier 3):** Post-interaction batch analysis is where red teaming compounds over time. Near-miss analysis catches interactions that passed all guardrails but came close to failing — surfacing emerging risk patterns before they become violations. Drift detection identifies when agent behavior shifts relative to baseline. These findings feed back into tighter Tier 1 rules and Tier 2 rubrics, closing the loop. This applies across all channels and verticals — voice calls, chat sessions, document processing batches, claims adjudication runs.

### Quality Rubric Schema

Tier 2 soft guardrails evaluate against weighted quality dimensions. The rubric structure and scoring mechanism are consistent across verticals; the dimensions and weights adapt.

Each dimension has severity levels and correction prompts — when a threshold is breached, the system can intervene in real-time (Tier 2) or flag for review (Tier 3).

**Rubric design principles:**
- Weights must sum to 1.0
- Every dimension needs a clear measurement definition and severity scale
- Correction prompts are pre-authored per dimension per severity level
- Rubrics are version-controlled and promoted through Authoring & Eval
- Business teams own dimension definitions; platform engineering owns the scoring infrastructure

### Multimodal Guardrail Considerations

The three-tier model applies across all interaction channels. Channel-specific considerations:

| Channel | Gate Pattern | Key Consideration |
|---|---|---|
| **Voice (front office)** | Pre-TTS gate — check before speaking | Latency-critical. Tier 2 must run parallel with speech synthesis. |
| **Chat / SMS (front office)** | Pre-send gate — check before delivering | Latency relaxes but attack surface widens: multi-turn manipulation, prompt injection via conversation. |
| **Email (front/middle office)** | Pre-send gate with batch review option | Can afford async Tier 2 checks. Higher regulatory scrutiny on written content. |
| **Document processing (back office)** | Pre-output gate — check before finalizing extracted/generated data | Accuracy-critical over latency. Tier 2 can run synchronously. |
| **Claims / transactions (back office)** | Pre-commit gate — check before writing to systems of record | Financial accuracy and regulatory compliance. Full Tier 1 deterministic check mandatory. |
